# デジタルサイネージシステム製品仕様書 兼 運用マニュアル

## 第1章：システム製品仕様

## 1.1 システム概要
本システムは、マンション等の工事現場に設置されたWindows 11搭載の65型デジタルサイネージに対し、遠隔の管理画面からリアルタイムに工事情報や資料PDF（A3/A4）を配信・一元管理する電子掲示板システムです。
本番運用を見据え、複数企業（テナント）が同一のサーバーを安全に共同利用できるマルチテナント隔離設計を採用しています。

## 1.2 サイネージ表示画面仕様
* **画面解像度・比率**：4K（3840×2160）を基準とし、アスペクト比16:9のあらゆる解像度に対応。文字や枠を自動で比例拡大（可変スケール）します。内部の初期計算順序を最適化し、起動時のクラッシュを完全に防いでいます。
* **上部ヘッダー（格子状テーブル）**：
  * 中央に「工事用掲示板」タイトルを大きな太字で配置。
  * 「工期（着工・完工日：年月日・曜日表記）」「現場代理人」「連絡先TEL」を綺麗な格子状の表組み（QTableWidget）で再現。
  * 項目名セルの背景は薄いグレー（#e6e6e6）、実際のデータが入るセルは白で構成し、文字は視認性の高い太字（Bold）で表示。
* **中間資料表示エリア（3区画独立ループ）**：横伸びバグを防ぐため絶対座標（setGeometry）で配置を厳格にロック。
  * 左区画（幅25%）：A4サイズ（作業内容等）
  * 中央区画（幅50%）：A3サイズ（図面・全体工程表等）
  * 右区画（幅25%）：A4サイズ（洗濯物情報等）
  ※各区画に2枚以上のPDFが登録されている場合、管理画面で物件ごとに指定された秒数間隔で個別に自動ループ再生（PyMuPDFによる高精細レンダリング）を行います。
* **下部フッターエリア（4大要素配置）**：
  * 左端：工事中イラスト（koujichu.png）を常時描画。
  * 中央左：スマホ閲覧用URLを元にQRコードを自動生成。枠内に適切な白い余白（マージン）を持って描写。下部の説明テキスト「読み取り用QRコード」の枠線は排除し、白地に文字のみのクッキリした透過配置を採用。
  * 中央右：登録された物件所在地に基づき、「当日」および「翌日」の天気予報を視認性の高い黒背景・白文字のボックス枠内にリアルタイム表示。
  * 右端：会社ロゴ（logo.png）を常時描画。

## 1.3 遠隔管理システム（ダッシュボード）仕様
* **セキュリティ認証（ログイン機能）**：管理画面へのアクセスにはユーザーIDとパスワードによる認証が必須。互換性を担保した安定版の `bcrypt==4.3.0` アルゴリズムにより、パスワードを安全にハッシュ化して保存します。
* **マルチテナントデータ隔離（データ秘匿）**：ログインしたユーザー（テナント）は、自身が登録した物件（現場）のみを閲覧・操作可能。他ユーザーの物件データやPDF原本の閲覧、URL直打ちによる不正操作を行うことはシステムレベルで完全に遮断されます。
* **物件（現場）切り替え機能**：最上部のプルダウンメニューから自身が管理対象としている物件（現場）を瞬時に切り替え可能。
* **物件の新規作成機能**：「物件名」「着工日」「完工日」「現場代理人」「連絡先」「物件所在地（天気連動用）」「ループ切替秒数」を入力し、無制限に現場を新規追加・一元管理。データは標準データベース（SQLite: contact_board.db）に保存。
* **ドラッグ＆ドロップ対応自動アップロード**：各区画に対応した専用枠にPDFを落とすだけで、選択ボタンを押さずとも、その場でサーバー内の物件IDごとに仕分けられたサブフォルダ（server_storage/{物件ID}/a3/ 等）へ物理保存。

## 1.4 通信・堅牢性（ポケットWi-Fi・セキュリティ対策仕様）
* **サイネージ専用トークン（パスキー）認証**：現場のサイネージPCがサーバーからデータを取得する際、物件ごとに自動生成される一意の40文字の暗号英数字（signage_token）をURLパラメーターに含めることが必須。これにより、第三者や別テナントが物件IDを推測してデータや図面ファイルを盗み見るクラッキング行為を完全に防ぎます。
* **スマート差分配信 ＆ 完全ローカルキャッシュ**：10MB以上の大容量PDF図面を扱うため、サイネージアプリはサーバーに新しい資料がある時だけバックグラウンドで差分ダウンロード（HTTP 304対応）を行います。データは現場PC内（signage_storage/{物件ID}/）に完全キャッシュされるため、現場のポケットWi-Fiが一時的に切断（オフライン状態）されても、サイネージの画面が白紙化することなく、3区画のループ表示を継続します。
* **AWS IMDSv2 自動IP追従**：サーバーの起動時に、AWS EC2の正規メタデータエンドポイント（http://169.254.169...）経由で現在のパブリックIPアドレスを自動検出。EC2を停止・再起動してパブリックIPが変更された場合でも、プログラムを一切書き換えることなく自動で最新のIPアドレスに追従します。

## 第2章：現場サイネージPC（Windows 11）自動起動設定手順

現場に設置するPCが、毎朝の主電源ONや再起動時に自動でWindowsのデスクトップ画面やタスクバーを隠し、対象の現場IDかつ専用トークンを用いて、文字や画像が比例拡大された「最前面フルスクリーン（キオスクモード）」で立ち上がるようにするための設定手順です。

## 2.1 起動用引数（パラメータ）仕様
サイネージアプリ（`signage_app.py`）は、完全に外部パラメータ（引数）による起動制御に対応しています。IPアドレスの変更やドメイン取得時にもコードの修正は不要です。

| 引数 | 必須/任意 | 説明 | 指定例 |
| :--- | :--- | :--- | :--- |
| `--id` | 任意 (デフォルト: 1) | 接続対象の工事物件（現場）IDを指定します。 | `--id 1` |
| `--token` | **必須** | セキュリティ認証用の所有権トークンを指定します。 | `--token a7f5de3b...` |
| `--server` | 任意 (デフォルト: `127.0.0.1:8000`) | 接続先サーバーのIPまたはドメインを指定します。 | `--server 13.196.186.120:8000` |
| `--kiosk` | 任意 | 有効にすると、枠なし最前面フルスクリーンで起動します。 | `--kiosk` |

## 2.2 起動用バッチファイル（.bat）の作成
1. プログラムが配置されているフォルダ（D:\TAIHEI）の中に、新しくテキストファイルを作成します。
2. ファイル名を `start_signage.bat` に変更します。
3. メモ帳で開き、以下の構成で記述して保存します。

```bat
@echo off
cd /d D:\TAIHEI
:: venv環境のアクティベート
call venv\Scripts\activate
:: 現場ID、専用セキュリティトークン、AWSサーバーを指定して全画面キオスクモードで起動
python signage_app.py --id 1 --token あたなの専用トークン文字列 --server 13.196.186.120:8000 --kiosk
```

※各現場固有の起動コマンド一式は、管理画面（/admin）の設定フォーム上部「📌 この現場のサイネージPC起動コマンド」ブロックから、**自動取得されたパブリックIP付きの文字列をワンクリックでそのままコピー＆ペースト可能**です。

## 2.3 Windows 11 スタートアップへの登録
PCの電源が入った際に、上記のバッチファイルを自動実行させます。
1. キーボードの `Windowsキー + R` を同時に押して「ファイル名を指定して実行」を開きます。
2. 入力欄に `shell:startup` と入力して「OK」を押します。
3. 先ほど作成した `start_signage.bat` のショートカットを作成し、このスタートアップフォルダの中に配置します。

## 2.4 運用時の終了方法（マニュアル）
キオスクモード起動時は、枠線や「×」ボタン、タスクバーがすべて隠れます。メンテナンス等でアプリを終了させたい場合は、PCにキーボードを接続し、以下のいずれかの隠しショートカットキーを押してください。
* キーボードの **`Esc` (エスケープ) キー** を1回押す。
* または、**`Ctrl` キーを押しながら `Q` キー** を押す。

## 第3章：AWS（クラウド）本番サーバー移行手順

AWSの契約が完了し、URL（ドメイン）が確定した段階で、本番サーバーへシステム一式を移行・公開する手順です。

## 3.1 推奨AWSインフラ構成
* **Amazon EC2（仮想サーバー）**：t3.medium (Ubuntu Server) ➔ `server.py` を24時間常駐稼働。
* **Amazon S3（堅牢ストレージ）**：大容量PDF原本を保管する領域。
* **Amazon Route 53 ＆ ACM**：確定した独自ドメインの紐付けと、通信の暗号化（https://〜 無料SSL証明書）の設定。

## 3.2 サーバー移行の手静（デプロイ）
1. **EC2インスタンス（Ubuntu）の起動**：HTTP(80)・HTTPS(443)・カスタムポート(8000)をセキュリティグループで解放。
2. **Route 53 ＆ ACM設定**：独自ドメインの紐付けとSSL証明書の発行。
3. **常駐化**：`server.py` とSQLiteデータベースを移行し、Linuxのサービス（systemd）として登録。
4. **現場PCのバッチファイル書き換え**：現場PC側で起動している `start_signage.bat` 内の `--server` パラメータ値を、IPアドレスから取得した独自ドメイン名（例: `example.com:8000`）へ差し替えます。

## 第4章：現場設置用ミニPC 推奨スペック
10MB以上の重い図面PDFをカクつきなく滑らかにループ再生させながら、現場の過酷な環境で24時間安定運用するためのハードウェア選定基準です。

## 4.1 スペック基準表
* **OS**：Windows 11 Pro (64bit) 【必須】※自動起動制御、リモート保守用
* **CPU**：Intel Core i5 (第12世代以降) または AMD Ryzen 5 以上 【推奨】
* **メモリ (RAM)**：16GB (DDR4 / DDR5) 【推奨】※4K大画面への図面展開・展開キャッシュに必須
* **ストレージ**：256GB または 512GB SSD (M.2 NVMe接続) 【推奨】
* **グラフィック**：Intel Iris Xe Graphics または AMD Radeon Graphics (4K/60Hz出力対応)

## 4.2 現場運用における注意点（熱・粉塵対策）
* **排熱・防塵対策**：モニター背面は熱がこもりやすく、さらに粉塵が舞いやすいため吸気口の詰まりによる熱暴走が多発します。故障を完全に防ぐためには、モニター裏への直接設置を避け、「防塵対策を施した現場用のプラスチックボックス等の中にミニPCを収め、長めのHDMIケーブルでモニターと接続する」構成での運用を強く推奨します。

## 第5章：AWSアカウントの作成手順（契約）

## 5.1 事前準備
* メールアドレス（会社の共有アドレス推奨）、クレジットカード、本人確認用電話番号。

## 5.2 開設ステップ
1. AWS公式（https://amazon.com ）から「AWSアカウントを無料で作成」を選択。
2. アカウントの種類で必ず「ビジネス」を選択し、会社名・住所をローマ字（英語表記）で入力。
3. 決済カード情報を登録し、自動音声通話（またはSMS）による本人確認を実行。
4. サポートプランで「ベーシックサポート（無料プラン）」を選択して完了。

## 第6章：独自ドメイン（本番用URL）の取得手順

## 6.1 Route 53 によるドメイン購入手順
1. AWS管理コンソールから「Route 53」ダッシュボードを開きます。
2. 左メニュー「登録済みドメイン」➔「ドメインの登録」を選択。
3. 希望する文字列を入力し、企業・システム用として最も一般的で信頼性の高い `.com`（年間約2,000円前後）を取得。
4. 所有者情報を入力し決済を確定。
5. 【最重要】届いたメール本文内の確認用リンクURLを必ず14日以内にクリックして承認を完了させます（忘れるとドメインが凍結されます）。

## 第7章：物件（現場）削除機能・誤動作防止仕様

複数拠点管理において、現場の管理ミスや誤操作によるデータ消失を防ぐための安全・堅牢仕様です。

## 7.1 警告確認ポップアップ（誤動作防止）
* 管理画面の設定フォーム内に、赤い「🚨 この物件を削除する」ボタンを設置。
* ボタン押下時、ブラウザ標準のダイアログが作動し、「⚠️ 警告: 物件を完全に削除しますか？」「🚨 本当に本当によろしいですか？」と連続して厳重な確認を要求することで、誤クリックによる現場データの誤消去を100%防止します。

## 7.2 データベース永久欠番仕様
* 削除が確定すると、データベース（SQLite）から該当物件のルーティングパス（FastAPI標準の一重波括弧 `{project_id}` 制御）が安全に消去され、サーバー内の物理フォルダ（`server_storage/{物件ID}/`）も中身のPDFごと丸ごと自動で物理消去されます。
* **物件IDの保持**：削除された物件のID（例: 2番）は、データベースの特性により「永久欠番（空き番号）」となります。その後、右側フォームから新しい現場を新規作成しても、過去の空きIDが詰められたり再利用されたりすることはなく、必ず新規の連番（3番、4番…）が発行されるため、サイネージPC側との通信やフォルダ構造の紐付けが重複・混ざるリスクを根底から排除しています。

## 第8章：管理者用テナント（ユーザー）アカウント新規発行手順

🔒 データベースがまだ空の初期状態（初回起動時）に限り、テスト用として以下の2つのデモアカウントが自動的に作成されるようになっています。
* ユーザーID: `admin` ／ パスワード: `admin123`
* ユーザーID: `user2` ／ パスワード: `pass123`

## 8.1 専用登録スクリプト（create_user.py）による新規ユーザー発行
管理画面への不正なアカウントインジェクションを防ぐため、セキュリティの観点から新規ユーザーの発行はサーバー内のコマンドラインインターフェース（CLI）からのみ実行可能です。

AWS本番サーバー（EC2）にSSHログインし、以下の手順で対話型スクリプトを実行して登録を行います。

1. **本番サーバーへのSSH接続**
   作業端末からAWS環境へSSH接続します。
   ```bash
   ssh -i /path/to/signage-key.pem ubuntu@13.196.186.120
   ```

2. **作業ディレクトリへの移動と仮想環境のアクティベート**
   ```bash
   cd ~/signage-app
   source venv/bin/activate
   ```

3. **登録スクリプトの実行**
   ```bash
   python create_user.py
   ```
   対話形式に従い、「希望するユーザーID」と「パスワード」を入力すると、パスワードが安全にハッシュ化（bcrypt）された上でデータベースの `users` テーブルへ直接インサートされます。

## 8.2 現在のユーザーID一覧（登録状況）の確認方法
現在システムに登録されている管理者ユーザーの一覧を確認する場合は、サーバー内でSQLiteデータベースへ直接クエリを発行して確認します。

1. **データベースへの接続**
   ```bash
   sqlite3 contact_board.db
   ```

2. **一覧確認コマンドの実行**
   ```sql
   .headers on
   .mode column
   SELECT id, username FROM users;
   ```
   *出力例:*
   ```text
   id          username  
   ----------  ----------
   1           admin     
   2           user2     
   ```

3. **SQLiteの終了**
   ```sql
   .exit
   ```

## 8.3 ユーザーID（テナントアカウント）の削除手順
運用を終了したテナントや、不要になったユーザーIDを完全に削除する手順です。アカウントを削除する前に、必ず「該当ユーザーが所有する物件データ」をすべて削除してください。

1. **データベースへの接続**
   ```bash
   sqlite3 contact_board.db
   ```

2. **【重要】事前確認（対象ユーザーの所有オブジェクト確認）**
   削除対象のユーザーID（例: `username = 'user2'`）が管理している物件が存在しないか確認。
   ```sql
   SELECT id, name FROM projects WHERE user_id = (SELECT id FROM users WHERE username = 'user2');
   ```
   ※物件がヒットした場合は、先に管理画面（/admin）より該当物件の「🚨 この物件を削除する」を実行し、物理フォルダの安全消去を完了させてください。

3. **ユーザー削除SQLの実行**
   対象のユーザーをデータベースから完全に削除します。
   ```sql
   DELETE FROM users WHERE username = 'user2';
   .exit
   ```

⚠️ **運用上の注意点**
ユーザーを削除すると、そのユーザーIDでダッシュボード（/admin）へのログインは一切行えなくなります。削除されたIDはデータベースの構造の整合性維持のため再利用されない安全設計となっています。
